Why: when config.yaml names a theme that is neither installed under ~/.config/familiar/themes/<id> nor shipped, every verb that resolves it, the hooks included, dies with `familiar: ENOENT: no such file or directory, realpath '<repo>/themes/cats'`. The path is the shipped-themes fallback, which has not existed in this repo since the split, so the message points at the wrong directory and names neither the theme nor the fix. `theme show` already says `unknown theme "cats" — available: (none)`, so the resolution path is the outlier. Reproduced 2026-10-17 with FAMILIAR_CONFIG_DIR holding only config.yaml (theme: cats), scheme.json and theme-receipts/cats.json: `familiar whoami` and `familiar hook SessionStart` both print the raw ENOENT. Observed live on europa 2026-10-16 (fam-fb393c).

Done: resolving a configured theme that is in neither root fails with one line that names the theme id, says it is not installed, and gives the recovery. When a validated receipt exists, the line names the receipt's source (URL and commit, or local path) and today's recovery (remove the receipt, then `familiar theme add <source>`); once fam-fb393c's restore lands, that becomes the restore command. With no receipt it names `familiar theme add SOURCE` and `familiar theme list`. An invalid receipt is reported as invalid, as `theme list` already does. Tests cover all three receipt verdicts through the resolution path; the line stays one line because hook stderr is all a user sees.

Where: themeDirFor in src/config.js (falls back to paths.themesDir unconditionally); the realpath call that loads the pack; readReceipt/receiptPath in src/theme/receipt.js; the receipt wording in bin/familiar.js `theme list`; the unknown-theme message behind `theme show`.
