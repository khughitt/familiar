Every Claude Code Stop maps to done (src/adapters/claude-code.js HOOK_EVENTS), so ending a turn to wait on a background subagent, workflow or shell plays the niri-desktop done popup (integrations/niri-desktop, transitions into done/error) and the niri done impulse (integrations/niri/signal.js), as if the work had finished. The user sees this as an alert at subagent launch.

Evidence (hq-d121c3, 2026-10-19, Claude Code 2.1.302): the Stop payload's background_tasks is documented in the bundle as in-flight background work (running/pending + backgrounded) so hooks can distinguish 'session is done' from 'session is paused waiting for background work to wake it'. Over 2026-10-17 22:00 to 2026-10-19 05:20, 73 main-session turn ends had pendingBackgroundAgentCount or pendingWorkflowCount >= 1, and each ran familiar hook Stop; a live example is hq session 0b615834 at 09:19:19Z (pendingBackgroundAgentCount 1, familiar Stop ran, record backgroundTasks 1). When the work completes Claude re-invokes the session and its final Stop arrives with nothing in flight, so done still fires once, at the real end.

Approach: reduce Stop with backgroundTasks > 0 to a non-impulse state (working is the natural reading: the agent is busy with its own work) instead of done, alongside the existing idle_prompt reduction. Also count status pending as in flight in payload.js runningBackgroundTasks, matching Claude's own predicate (running or pending). Keep the done popup and pulse for a Stop with nothing in flight, and keep BEL behaviour unchanged.

Verification: adapter/transaction tests for Stop with a running subagent, a pending task, a shell, and an empty list; the existing idle_prompt reduction still holds. Codex is out of scope (its turn does not end while it waits on its subagents).
